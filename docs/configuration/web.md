# Веб-приложение: секция `web`

Генератор и раньше умел **раздавать** фронтенд — транспорт `generator_template: static`
отдаёт каталог проекта по HTTP ([Раздача статики](transports.md#раздача-статики-templatestatic)).
Откуда в этом каталоге берутся файлы, он не знал: сборки фронта не было, кодогенерации
TS-клиента из спек, которые генератор же забирает в `rest:` и `jsonschema:`, — тоже. Каждый
проект закрывал это по-своему: npm-скрипты вне `make generate` (и закоммиченный клиент
отставал от спеки, пока кто-нибудь не запустит npm руками), сборка фронта make-пререквизитом
в пользовательской секции либо свой Dockerfile с node-стадией.

Секция `web` объявляет фронтенд как сущность: где исходники, чем ставить зависимости, чем
собирать, куда складывать результат и из каких входов генерировать клиент. Команды — проектные,
как в [`generator`](custom-generators.md): генератор владеет проводкой (make-цели, стадия сборки
в образе), а не выбором сборщика и генератора клиента.

Без секции `web` вывод не меняется ни на байт.

## Пример

```yaml
web:
  - name: admin
    dir: web/admin            # исходники фронта (проектные, генератор их не создаёт)
    install: npm ci           # опционально
    build: npm run build      # обязательно; пишет в output
    output: static            # каталог, который раздаёт транспорт static
    node_image: node:22-alpine  # опционально
    codegen:                  # опционально; команда — своя на каждый канал
      rest:
        cmd: npx openapi-typescript {{ .Spec }} -o src/api/{{ .SpecName }}.ts
        inputs: [api]         # входы rest[], которые потребляет фронт
      jsonschema:
        cmd: npx json2ts {{ .Spec }} -o src/models/{{ .SpecName }}.d.ts
        inputs: [models]      # входы jsonschema[]

rest:
  - name: api
    path: [git+ssh://git@github.com/org/contracts.git#rest/api.yaml]
    version: "v1"
    port: 8080
    generator_type: ogen
  - name: static
    port: 8086
    version: "v1"
    generator_type: template
    generator_template: static
    generator_params:
      dir: static

jsonschema:
  - name: models
    schemas:
      - id: user
        path: ./user.schema.json

applications:
  - name: api
    transport:
      - name: api
      - name: static
```

## Поля

| Поле | Обяз. | Описание |
|------|-------|----------|
| `name` | да | Имя фронтенда. `^[a-z0-9_-]+$`. Становится суффиксом make-целей и именем стадии Dockerfile. |
| `dir` | да | Каталог исходников от корня проекта. **Все** команды записи выполняются в нём. |
| `install` | нет | Установка зависимостей (`npm ci`, `yarn install --frozen-lockfile`). Она же делает доступным инструмент кодогена. |
| `build` | да | Сборка фронта в `output`. |
| `output` | да | Каталог, в который пишет сборка. Должен раздаваться транспортом `static` какого-нибудь приложения. |
| `node_image` | нет | Базовый образ стадии сборки. По умолчанию `node:22-alpine`. |
| `codegen` | нет | Генерация клиента из входов проекта (ниже). |

`install` и `build` переменных шаблона не принимают: они выполняются один раз на фронтенд,
а не на спеку.

**Каждая команда — одна строка.** Она становится одной строкой make-рецепта и одной инструкцией
`RUN` в Dockerfile: перенос строки (в том числе YAML-блоком `|`) оставил бы хвост команды
невыровненной строкой Makefile — `missing separator`, и не работает уже ни одна цель проекта.
Поэтому многострочная команда — ошибка загрузки конфига. Нужна последовательность шагов —
соедините их через `&&` или вынесите в скрипт проекта.

**`$` в командах раскрывает make.** `$HOME` в рецепте превращается в `OME`; чтобы знак доллара
дожил до шелла, его удваивают: `$$HOME`. То же самое в секции
[`generator`](custom-generators.md).

`output` — каталог в корне проекта, и его имя подчиняется правилам `generator_params.dir`
транспорта `static`: только нижний регистр `[a-z0-9_-]`, начинается с буквы (он обязан совпасть
с объявленным там каталогом).

**`output` обязан кто-то раздавать.** Каталог, который не раздаёт ни один транспорт `static`, —
это сборка, результат которой никуда не попадает: ни в ответ сервиса, ни в образ. Генерация
падает на загрузке конфига. Привязка фронтенда к приложению из этого и выводится — объявлять её
второй раз не нужно: фронт собирается в образе того приложения, которое раздаёт его `output`.

**Один `output` — один фронтенд.** Две записи с одинаковым `output` пишут в один каталог: в
образе выигрывает та стадия, которую скопировали последней, локально — та сборка, которая
отработала последней. Это ошибка конфига.

**`dir` не может лежать внутри `output`.** Каталог сборки принадлежит сборке: он целиком уходит
в `.gitignore` (`<output>/*`) и перезаписывается в образе результатом node-стадии. Исходники в
нём молча перестали бы версионироваться, поэтому `dir: static` при `output: static` (и любой
вложенный `dir: static/src`) — ошибка загрузки конфига.

## Кодоген клиента: `codegen`

`codegen` состоит из **каналов** — `rest` и `jsonschema`. Каждый канал объявляет свою команду и
свои входы:

| Поле | Обяз. | Описание |
|------|-------|----------|
| `codegen.rest` | — | Канал входов `rest[]`. |
| `codegen.jsonschema` | — | Канал входов `jsonschema[]`. |
| `<канал>.cmd` | да | Команда генерации; выполняется по одному разу на **каждый файл спеки** каждого входа канала. |
| `<канал>.inputs` | да | Имена записей соответствующей секции, которые потребляет фронт. |

Хотя бы один канал обязателен, и в канале обязателен хотя бы один вход: кодоген без входов
ничего не генерирует.

**Почему команда на канал, а не одна на обе секции.** Генератор TS читает **один** из двух
форматов: `openapi-typescript` — OpenAPI, `json-schema-to-typescript` (`json2ts`) — JSON Schema.
Единственная команда на оба канала падает на первой же спеке «чужого» формата
(`Unsupported schema format, expected openapi: 3.x`), а `generate-web-<name>` входит в
`generate` — вместе с ней падает весь `make generate` (и `make regenerate`).

Одно имя может встречаться в обоих каналах: это разные входы разных секций, и генерируются они
разными командами.

**Входы называются по имени, не по пути.** Вход — это спека, которую генератор **уже** забрал и
положил в проект (`api/rest/<имя>/<версия>/…`, `api/schema/<имя>/…`). Второй копии той же спеки
не появляется — ровно поэтому для этого случая не годится `contract:`, которому нужен свой `path`
и своя `copy`.

### Переменные в `cmd`

- `{{ .Spec }}` — путь копии спеки **относительно `dir`** (команда выполняется в `dir`),
  например `../../api/rest/api/v1/api.swagger.yml`;
- `{{ .SpecName }}` — basename этой копии без расширения (`api.swagger`);
- `{{ .Input }}` — имя записи того канала, которой принадлежит файл.

Шаблон проверяется при загрузке конфига: неизвестная переменная или незакрытое `{{` — ошибка
загрузки, а не пустая строка в команде. Отрендеренная команда должна быть одной строкой — это
одна строка make-рецепта.

Поля `target` здесь нет намеренно: вход может принести несколько файлов (несколько `path` у
`rest[]`, несколько `schemas` у `jsonschema[]`), и единственный путь вывода они бы перезаписали
друг другом. Путь вывода собирается в команде из `.SpecName` / `.Input`.

## Make-цели: одна на фронтенд

- `install-web-<name>` — если задан `install`; добавляется в зависимости `install-tools`;
- `build-web-<name>` — сборка фронта;
- `generate-web-<name>` — если задан `codegen`; добавляется в `generate` (и через него в
  `regenerate`) **после** встроенных генераторов: клиент генерируется из спек, которые они
  только что обновили.

Для примера выше:

```make
.PHONY: install-web-admin
install-web-admin:
	cd web/admin && npm ci

.PHONY: build-web-admin
build-web-admin:
	cd web/admin && npm run build

.PHONY: generate-web-admin
generate-web-admin:
	cd web/admin && npx openapi-typescript ../../api/rest/api/v1/api.yaml -o src/api/api.ts
	cd web/admin && npx json2ts ../../api/schema/models/user.schema.json -o src/models/user.schema.d.ts
```

**`generate-web-<name>` требует node в окружении `make generate`.** `make regenerate` с
`call_generate` в `post_generate` вызывает `make generate`, то есть и кодоген фронта: образ, в
котором это запускается, должен уметь выполнить объявленную команду. Сам образ приложения
собирается без node на хосте — см. ниже.

## Сборка в образе: стадия node

`docker-<app>` **не** зависит от `build-web-<name>`: фронт собирается в своей стадии внутри
Dockerfile приложения, которое раздаёт его `output`. Так образ несёт тот фронт, который описан
исходниками, а не тот, что остался в рабочем каталоге; node на хосте (и в CI-раннере) не нужен;
node-тулчейн не попадает в runtime-образ.

```dockerfile
FROM node:22-alpine AS web-admin
WORKDIR /src
COPY . .
RUN cd web/admin && npm ci
RUN cd web/admin && npm run build

FROM golang:1.27-alpine AS builder
# …
RUN mkdir -p /static
ADD static /static
RUN chmod -R 755 /static

COPY --from=web-admin /src/static/ /static/
RUN chmod -R 755 /static

FROM alpine
COPY --from=builder /static /static
```

- стадия копирует весь контекст (`COPY . .`), как и builder-стадия: сборка фронта читает не
  только `dir` (сгенерированный клиент, общие конфиги), и какие именно файлы — дело проекта;
- копия идёт **после** `ADD <output>`: поверх того, что лежит в каталоге в контексте сборки,
  ложится результат сборки — он и есть источник истины о том, что раздаётся;
- `make build-web-<name>` остаётся для локального цикла: собрать фронт и поднять сервис
  через `make run-<app>`.

Клиент, сгенерированный `generate-web-<name>`, в проекте **коммитится** — стадия node его не
генерирует, она его читает из контекста.

## Регенерация и git

Каталог `output` остаётся пользовательским: генератор не читает и не трогает его содержимое при
`make regenerate` (кроме болванки `<output>/.keep`, которая держит каталог в контексте сборки).
В `.gitignore` нового проекта попадают `node_modules/` и `<output>/*` с исключением
`!<output>/.keep` — результат сборки версионировать не нужно, а каталог должен существовать.

`.gitignore` генерируется один раз и дальше принадлежит проекту: в **существующий** проект эти
строки нужно добавить руками.
