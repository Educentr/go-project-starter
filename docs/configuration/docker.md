# Docker

## Зачем

Образу нельзя было штатно сообщить его собственную идентичность — версию и
ревизию (OCI `org.opencontainers.image.version` / `.revision`). `LABEL`
статичен и не умеет вызвать `git`, поэтому значения обязаны приехать через
`--build-arg`, а стадия, которая их использует, обязана объявить `ARG`. Ни
того, ни другого выразить было нечем:

- шаблон Dockerfile объявлял в builder-стадии только `ARG binary` и
  `ARG GOPROXY`;
- сгенерированный рецепт `docker-<app>` звал `docker build` без единого
  `--build-arg`;
- секция `docker:` несла единственное поле `image_prefix`.

Пользовательский маркер спасает только то, что лежит **ниже** него, то есть
финальную стадию; builder-стадия целиком генерируемая, поэтому дописанный туда
`ARG` пропадал на каждом `make regenerate` — молча, вместе со своим
комментарием. Потребителю оставался скрипт-overlay, который заново вставляет
`ARG` по якорю, плюс переопределённые копии рецептов `docker-<app>` с
дописанным `--build-arg`.

`build_args` и `labels` объявляют это в `project.yaml` — один раз на проект, с
генерацией во всех четырёх местах сразу.

Платформа образа была ничем не выразима по той же причине. Builder-стадия
собиралась без `--platform=$BUILDPLATFORM` и без `ARG TARGETARCH`, рецепты
`docker-<app>` звали `docker build` без `--platform`, так что образ получался
под платформу сборщика — а приложение, которое запускают и на amd64, и на
arm64, этим не поставить. Потребителю оставался тот же overlay: скрипт, который
после каждой регенерации дописывает `--platform=$BUILDPLATFORM` и
`ARG TARGETARCH` в генерируемую зону Dockerfile, плюс переопределённые на
`buildx` цели публикации. `platforms` объявляет это у приложения.

## Параметры

```yaml
docker:
  image_prefix: registry.example/org   # префикс образов (REGISTRY_SERVER), по умолчанию educentr
  build_args:
    - IMAGE_VERSION                    # короткая форма: только имя
    - name: IMAGE_REVISION             # полная форма
      default: $(shell git rev-parse HEAD)
      stages: [builder, final]
  labels:
    org.opencontainers.image.version: ${IMAGE_VERSION}
    org.opencontainers.image.revision: ${IMAGE_REVISION}
    org.opencontainers.image.vendor: Educentr
```

Платформы образа объявляются не здесь, а у приложения — его образ собирают под
те платформы, где его запускают:

```yaml
applications:
  - name: cli
    docker:
      platforms: [linux/amd64, linux/arm64]
```

Все три секции опциональны. Без них вывод побайтно совпадает с прежним, поэтому
регенерация существующих проектов ничего не меняет.

### `build_args`

Список объявленных build-аргументов образа. Элемент — либо имя, либо объект:

| Поле | Обязательное | Значение |
|---|---|---|
| `name` | Да | Имя аргумента. Оно же — имя `ARG` в Dockerfile, переменной в Makefile и ключа `--build-arg`. Допустимы `[A-Za-z_][A-Za-z0-9_]*` |
| `default` | Нет | Значение по умолчанию в Makefile (`<name> ?= <default>`). Может быть make-функцией, например `$(shell git rev-parse HEAD)` |
| `stages` | Нет | Стадии Dockerfile, которые объявляют `ARG`: `builder`, `final` или обе. По умолчанию `[final]` |

Из каждого аргумента генерируются:

1. `ARG <name>` в перечисленных стадиях Dockerfile;
2. `--build-arg <name>="$(<name>)"` в рецепте `docker-<app>`;
3. `<name> ?= <default>` в Makefile — локальная сборка не требует передавать
   значение руками, а `?=` оставляет приоритет за переменной окружения или
   командной строкой (так его переопределяет CI);
4. `<name>=${<name>:-}` в `build.args` приложения в `docker-compose-dev.yaml`
   (compose не умеет вычислять make-дефолт, поэтому значение берётся из
   окружения и пусто, если не задано).

**Почему по умолчанию только `final`.** `ARG` обесценивает build-кеш всех слоёв
стадии, которые идут **после** него, а версия и ревизия меняются на каждом
коммите. Лейблы живут в финальной стадии, и там `ARG`-блок генерируется в самом
конце стадии — после `COPY`/`CMD`/`EXPOSE`, так что смена значения не
перекомпилирует образ. `stages: [builder, final]` нужен только тогда, когда
значение реально требуется при сборке бинарника (например уходит в `ldflags`), и
стоит это осознанного инвалидации кеша builder-стадии.

Имя не может совпадать ни с `ARG`-ами шаблона Dockerfile (`binary`, `GOPROXY`),
ни с переменными, которые объявляет сгенерированный Makefile (`DOCKER_TAG`,
`RELEASE`, `SERVICE_NAME`, …) — иначе объявление переопределило бы значение,
которым пользуется остальная сборка. Такие имена отвергаются на загрузке
конфига.

### `labels`

Карта `ключ: значение` → одна инструкция `LABEL` (один слой) в финальной стадии.
Значение может ссылаться на build-аргумент (`${IMAGE_VERSION}` или
`$IMAGE_VERSION`); литерал `$` экранируется как `$$`.

**Ссылка проверяется на загрузке конфига:** если значение упоминает аргумент,
которого нет в `build_args` или который не объявлен в стадии `final`, генерация
падает с ошибкой. В финальной стадии значение больше взять негде, поэтому иначе
лейбл молча отрендерился бы пустым — ровно та поломка, из-за которой секция и
появилась.

Ключи — в нижнем регистре (viper приводит ключи конфига к нижнему регистру, так
что ключ с большой буквой молча изменился бы по дороге), из символов
`[a-z0-9._-]`. Значения — однострочная строка без `"` и `\` (на этих символах
ломается генерируемая инструкция).

## `platforms`

Платформы, под которые собирается образ приложения. Ключ — **per-application**
(`applications[].docker.platforms`), а не на весь проект: приложение, которое
запускают на машинах разработчиков (CLI-инструмент, поставляемый образом),
должно работать и на amd64, и на arm64 (Apple Silicon), а серверным приложениям
того же проекта обычно хватает одной платформы, и платить за вторую сборку им
незачем.

```yaml
applications:
  # Без ключа: образ собирается под платформу сборщика, как и раньше.
  - name: api
    transport:
      - name: api
  # Несколько платформ: образ — OCI index под одним тегом.
  - name: cli
    cli: admin
    docker:
      platforms: [linux/amd64, linux/arm64]
  # Одна платформа: кросс-сборка, но обычный образ.
  - name: tool
    transport:
      - name: sys
    docker:
      platforms: [linux/arm64]
```

Элемент — `linux/<arch>`, например `linux/amd64`, `linux/arm64`,
`linux/ppc64le`. Дубликаты запрещены. Отвергается на загрузке конфига:

- **другая ОС** (`darwin/arm64`, `windows/amd64`) — сгенерированный Dockerfile
  описывает linux-образ, образ под другую ОС не заработает, что бы ни было
  объявлено;
- **вариант архитектуры** (`linux/arm/v7`) — вариант не доезжает до сборки:
  builder-стадия берёт архитектуру из `TARGETARCH`, а сопоставления `v7` →
  `GOARM` нет, поэтому объявление молча собрало бы бинарь под другую
  суб-архитектуру.

Платформы у приложения, которое **не** собирает docker-артефакт (`artifacts`
без `docker`), — тоже ошибка генерации: ключ формирует рецепты образа, то есть
из него не сгенерировалось бы ничего.

### Что генерируется

**Dockerfile приложения** — кросс-компиляция вместо эмуляции. Go кросс-компилирует
сам, поэтому QEMU не нужен и сборка идёт на полной скорости:

- `FROM --platform=$BUILDPLATFORM golang:<ver>-alpine AS builder` — builder
  работает на платформе сборщика;
- `ARG TARGETARCH` и `GOARCH=${TARGETARCH:?…}` перед `make build_in_docker-<app>`.
  Форма `:?` — гвард: пустой `TARGETARCH` (сборка не через BuildKit) роняет
  сборку, вместо того чтобы молча собрать бинарь под архитектуру сборщика;
- **стадия сборки фронта** (`web-<name>`, если приложение раздаёт фронт секции
  [`web`](web.md)) тоже закреплена за платформой сборщика:
  `FROM --platform=$BUILDPLATFORM <node_image> AS web-<name>`. Незакреплённую
  стадию BuildKit собрал бы по разу на каждую целевую платформу, под эмуляцией;
  результат сборки фронта — статика, от архитектуры не зависит, поэтому хватает
  одного нативного прогона (подробности —
  [Стадия фронта и `platforms`](web.md#стадия-фронта-и-platforms));
- **runtime-стадия по умолчанию не выполняет `RUN`** — `RUN` там исполняется
  для целевой архитектуры и потребовал бы эмуляции. Каталог `/etc/onlineconf`
  создаётся в builder-стадии и копируется (`COPY --from=builder`) во всех
  проектах, независимо от `platforms`. Единственный `RUN`, который может
  появиться в финальной стадии, — установка `packages` (см.
  [Runtime-стадия приложения](#runtime-стадия-приложения-applicationsdocker));
  для чужой платформы он пойдёт через эмуляцию, поэтому объявлять `packages`
  вместе с `platforms` стоит только тогда, когда рантайм-зависимость
  действительно нужна.

**Makefile** — сборка через `docker buildx` с явным `--platform`:

| | `docker-<app>` | `docker-<app>-push` |
|---|---|---|
| без `platforms` | `docker build` | `docker push` |
| одна платформа | `buildx build --platform <p> --load` | `docker push` |
| несколько | `buildx build --platform <список> --output type=cacheonly` | `buildx build --platform <список> --push` |

Одна платформа — обычный образ, он попадает в локальное хранилище (`--load`), и
публикация остаётся прежним `docker push`. Несколько платформ — OCI index, а его
локальное хранилище образов держать не умеет: сборка остаётся в кеше билдера
(`--output type=cacheonly`), а публикует index **сама сборка** с `--push`, под
одним тегом. Порядок стадий CI (`make docker-<app>` → `make docker-<app>-push`)
при этом не меняется: вторая сборка переиспользует кеш первой.

Цели с `platforms` зависят от `buildx-builder` — он создаёт билдер
`$(BUILDX_BUILDER)` (по умолчанию `$(SERVICE_NAME)-builder`) с драйвером
`docker-container`, если его ещё нет. Драйвер по умолчанию (`docker`) не умеет
ни собирать под чужую платформу, ни держать index. Билдер переиспользуется;
удалить — `docker buildx rm $(BUILDX_BUILDER)`.

## Что получается на выходе

Для конфига из примера выше:

```dockerfile
# Dockerfile-api, builder-стадия
FROM golang:1.24-alpine AS builder
ARG binary=bin/api
ARG GOPROXY
ARG IMAGE_REVISION
```

```dockerfile
# Dockerfile-api, финальная стадия — ARG-блок и LABEL в самом конце
EXPOSE 8080

ARG IMAGE_VERSION
ARG IMAGE_REVISION

LABEL org.opencontainers.image.revision="${IMAGE_REVISION}" \
      org.opencontainers.image.vendor="Educentr" \
      org.opencontainers.image.version="${IMAGE_VERSION}"
```

```makefile
# Makefile
REGISTRY_SERVER ?= registry.example/org
DOCKER_TAG ?= $(ENVIRONMENT_PREFIX)$(RELEASE)-$(LAST_COMMIT_HASH)
IMAGE_VERSION ?=
IMAGE_REVISION ?= $(shell git rev-parse HEAD)

docker-api:
	DOCKER_BUILDKIT=1 docker build . -f ./Dockerfile-api --rm --secret id=github_token,env=GITHUB_TOKEN --build-arg IMAGE_VERSION="$(IMAGE_VERSION)" --build-arg IMAGE_REVISION="$(IMAGE_REVISION)" -t $(REGISTRY_SERVER)/$(SERVICE_NAME)-api:${DOCKER_TAG}
```

Передать значение сборке:

```bash
make docker-api IMAGE_VERSION=v1.2.3          # аргументом make
IMAGE_VERSION=v1.2.3 make docker-api          # переменной окружения (её же использует CI)
```

Аргумент без `default` и без переданного значения уедет в образ пустым — это
выбор конфига, а не ошибка. Если лейбл обязан быть заполнен всегда, задайте
`default`.

## Runtime-стадия приложения (`applications[].docker`)

Финальная стадия сгенерированного `Dockerfile-<app>` была зафиксирована:
`FROM alpine` и `CMD ["/service"]`. Приложению, которому нужен другой дистрибутив
или рантайм-зависимость (`git`, `curl`, `ca-certificates`), сказать об этом было
нечем: стадия генерируется, а пользовательский маркер спасает только то, что
лежит **ниже** него. Оставался обходной путь — отдельный
`Dockerfile-<app>.custom` плюс переопределённая цель `docker-<app>` в секции
после маркера.

```yaml
applications:
  - name: vt
    docker:
      base_image: ubuntu:24.04       # по умолчанию alpine
      packages:                      # рантайм-пакеты
        - git
        - curl
        - ca-certificates
      package_manager: apt           # опционально; выводится из base_image
      workdir: /workspace            # по умолчанию нет WORKDIR (докеровский "/")
      entrypoint: ["/service"]       # по умолчанию CMD ["/service"]
```

Секция опциональна и объявляется **у приложения**, а не у проекта: образы
приложений одного сервиса собираются из разных наборов зависимостей. Приложение
без секции получает прежнюю стадию — `FROM alpine` и `CMD ["/service"]`.

Одна строка финальной стадии при этом изменилась у **всех** проектов: каталог
`/etc/onlineconf` теперь создаётся в builder-стадии и приезжает в финальную через
`COPY --from=builder /etc/onlineconf /etc/onlineconf` вместо
`RUN mkdir -p /etc/onlineconf` (владелец и права те же — `root:root`, `0755`).
Это нужно, чтобы финальная стадия не требовала shell: без `packages` в ней не
остаётся ни одной инструкции `RUN`, и базовым образом может быть
shell-less образ (`gcr.io/distroless/static`, `scratch`) — самый частый рантайм
для статического Go-бинарника. Сборку это не меняет, только содержимое
`Dockerfile-<app>`.

Настраивается только финальная (runtime) стадия. Builder-стадия компилирует
статический Go-бинарник, и её базовый образ определяет `tools.golang_version`.

| Поле | Обязательное | Значение |
|---|---|---|
| `base_image` | Нет | Базовый образ runtime-стадии (`FROM`). По умолчанию `alpine`. Ссылка без пробелов, кавычек и `#` — допустимы registry с портом, тег и digest |
| `packages` | Нет | Рантайм-пакеты. Ставятся **одной** инструкцией `RUN` до копирования бинарника, поэтому слой переиспользуется, пока не изменится сам список. Порядок — как в конфиге. Допустим пин версии (`curl=8.5.0-2`). Требует от `base_image` shell и пакетного менеджера — для shell-less образа объявлять нечем, см. ниже |
| `package_manager` | Нет | Чем ставить: `apk`, `apt` или `dnf`. Выводится из `base_image` для `alpine`, `debian`, `ubuntu`, `fedora`; для любого другого образа **с пакетным менеджером** и объявленными `packages` — объявить явно |
| `workdir` | Нет | `WORKDIR` runtime-стадии, абсолютный путь. По умолчанию инструкция не генерируется (докеровский дефолт `/`) |
| `entrypoint` | Нет | `ENTRYPOINT` в exec-форме. **Заменяет** `CMD`, а не дополняет его: Docker передаёт `CMD` энтрипойнту аргументами, поэтому дефолтный `/service` приехал бы энтрипойнту параметром |

**Почему `package_manager` не угадывается для произвольного образа.** Менеджер
выводится из имени репозитория образа (`registry.example:5000/mirror/ubuntu:24.04`
→ `ubuntu`) и только для дистрибутивов, у которых он однозначен. Для
собственного или производного базового образа (`registry.example/org/base:2024`)
угаданный менеджер дал бы Dockerfile, который падает на сборке, — поэтому
генерация останавливается с требованием объявить менеджер. Объявленный
`package_manager` без `packages` — тоже ошибка: ставить нечего.

**Shell-less образ и `packages` несовместимы.** `gcr.io/distroless/...` и
`scratch` не содержат ни shell, ни пакетного менеджера, поэтому `packages` для
них не объявляются вовсе — объявленный `package_manager` тут не помогает, `RUN`
в таком образе падает с `/bin/sh: no such file or directory`. Рантайм-зависимость
для такого образа добирается иначе: либо берётся вариант базового образа, который
её уже несёт (`gcr.io/distroless/static` поставляется с `ca-certificates`), либо
нужные файлы доставляются в финальную стадию ручным `COPY --from=builder` в
секции после маркера. Без `packages` финальная стадия вообще не содержит `RUN`,
поэтому такой образ собирается.

Значения проверяются на загрузке конфига: образ и рабочий каталог — без пробелов
и кавычек, имена пакетов — из `[A-Za-z0-9._+-=:~/]`, элементы `entrypoint` —
непустые однострочные строки без `"` и `\`. Всё это попадает в инструкции
Dockerfile как есть, поэтому строка с пробелом или кавычкой ломала бы файл (а в
`RUN` — дописывала бы команду).

### Что получается на выходе

Для примера выше:

```dockerfile
# Dockerfile-vt, финальная стадия
FROM ubuntu:24.04

# Runtime packages, declared in the docker section of the application in
# project.yaml. Installed before the binary is copied, so the layer is reused
# until the package list itself changes.
RUN set -eux && \
    apt-get update && \
    DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends git curl ca-certificates && \
    rm -rf /var/lib/apt/lists/*

COPY --from=builder /service /service
COPY --from=builder /public /public
# Copying the directory from a stage keeps the ownership and mode it has there
# (root:root, 0755) — the same a `mkdir -p` in this stage would have given.
COPY --from=builder /etc/onlineconf /etc/onlineconf
WORKDIR /workspace
ENTRYPOINT ["/service"]
```

Индекс/кеш пакетного менеджера удаляется в той же инструкции (`rm -rf
/var/lib/apt/lists/*` для apt, `dnf clean all` для dnf, `--no-cache` для apk):
отдельный `RUN` оставил бы скачанные метаданные в слое ниже.

Приложение без секции `docker` получает прежнюю стадию — `FROM alpine` и
`CMD ["/service"]`.

Для shell-less образа (`packages` не объявлены) `RUN` в стадии не остаётся
вообще:

```dockerfile
# Dockerfile-vt, финальная стадия для base_image: gcr.io/distroless/static
FROM gcr.io/distroless/static
COPY --from=builder /service /service
COPY --from=builder /public /public
COPY --from=builder /etc/onlineconf /etc/onlineconf
CMD ["/service"]
```

## Проектные дополнения runtime-стадии (`copy`, `env`, `fetch`, `stages`)

`base_image` и `packages` закрывают образ, которому нужен другой дистрибутив и
пакеты из его репозиториев. Живой случай потребителя (#14) шире: в образ нужны
**каталоги проекта** (`template/` → `/opt/<app>/template` плюс `ENV`,
указывающий на него), **бинарь из релиза** по прямой ссылке с закреплённой
версией и архитектурой в имени файла, и **CLI-инструменты из npm**, которые
ставятся в отдельной стадии и копируются в runtime. Ни того, ни другого, ни
третьего выразить было нечем, и оставался всё тот же обход — рукописный
`Dockerfile-<app>.custom` плюс переопределённая цель `docker-<app>`.

Четыре ключа ниже объявляют это декларативно:

```yaml
applications:
  - name: api
    docker:
      base_image: ubuntu:24.04
      packages: [nodejs]
      platforms: [linux/amd64, linux/arm64]

      # Каталоги проекта в образ.
      copy:
        - from: template
          to: /opt/api/template

      # Переменные окружения runtime-стадии — обычно то, что указывает
      # приложению на принесённые каталоги.
      env:
        - name: API_TEMPLATE_DIR
          value: /opt/api/template

      # Файл по URL: версия закреплена в ссылке, архитектура — в имени файла,
      # контрольная сумма своя на каждую платформу.
      fetch:
        - name: tool
          url: https://github.com/org/tool/releases/download/v1.2.3/tool-linux-${TARGETARCH}
          to: /usr/local/bin/tool
          checksum:
            linux/amd64: sha256:1111…
            linux/arm64: sha256:2222…

      # Инструмент, которого нет ни в одном пакетном менеджере: ставится в
      # своей стадии, в runtime попадает копированием. Архитектура цели
      # переводится в словарь npm (`amd64` → `x64`, `386` → `ia32`), а префикс
      # копируется целиком — в его `bin/` лежат относительные симлинки.
      stages:
        - name: npmtools
          image: node:22-alpine
          run:
            - npm install -g --prefix /opt/npm --os=${TARGETOS} --cpu=$(case "${TARGETARCH}" in amd64) echo x64;; 386) echo ia32;; *) echo "${TARGETARCH}";; esac) some-cli@3.3.3
          copy:
            - from: /opt/npm
              to: /usr/local
```

Все четыре опциональны. Приложение без них получает побайтно прежний
`Dockerfile-<app>` (пин — `TestGenerateWithoutDockerAdditions`).

### Почему ключи, а не фрагмент Dockerfile

Исходное предложение в issue — проектный фрагмент (`Dockerfile-<app>.runtime`),
который генератор вставляет в финальную стадию. Он покрывает всё сразу, но
снимает то, за что заплатили `base_image`/`packages` и `platforms`: генератор
знает, что в финальной стадии **нет `RUN`**, и именно поэтому там собирается
shell-less база (`gcr.io/distroless/static`, `scratch`) и не нужен QEMU при
кросс-сборке. Фрагмент эту гарантию снимает, а проверить её генератор больше не
может — он не знает, что внутри. Плюс фрагмент после `FROM` всё равно не умеет
добавить стадию **до** финальной, а п.2 (npm) её требует.

Ключи ниже эмитят в финальную стадию только `COPY` и `ENV` — ни одной
новой `RUN`. Оба инварианта сохраняются по построению. Там, где `RUN` реально
нужен (установка инструмента), он уезжает в отдельную стадию, закреплённую за
платформой сборщика.

### `copy`

| Поле | Обязательное | Значение |
|---|---|---|
| `from` | Да | Каталог проекта, путь относительно корня (как `web.dir`) |
| `to` | Да | Абсолютный путь в образе |

Генерируется одна инструкция `COPY <from> <to>` в финальной стадии. **Не**
`ADD` и **не** транзит через builder-стадию:

- `COPY` не требует ни shell, ни целевой архитектуры, поэтому инвариант
  (shell-less база, никакой эмуляции) держится и без builder'а, в отличие от
  `StaticDirs`, которым builder нужен ради `chmod`;
- транзит через builder означал бы, что каталог проекта ложится в
  builder-образ по пути `<to>`: назначение вида `/usr/local` перезаписало бы
  там Go-тулчейн, и перезаписанное уехало бы в runtime;
- `ADD` распаковывает локальные tar-архивы, то есть на `from`, указывающем на
  архив, тихо делал бы не то, что написано.

Владелец — `root:root`, режимы приезжают из контекста сборки как есть (git
отслеживает только бит исполнения).

Существование каталога генератор не проверяет: он может создаваться самим
проектом или собираться другим инструментом. Отсутствующий каталог уронит
`docker build`, а не генерацию.

### `env`

| Поле | Обязательное | Значение |
|---|---|---|
| `name` | Да | Имя переменной, `[A-Za-z_][A-Za-z0-9_]*` |
| `value` | Нет | Значение; однострочное, без `"` и `\` |

Список `{name, value}`, а **не** карта `ИМЯ: значение` — viper приводит ключи
конфига к нижнему регистру, поэтому `API_TEMPLATE_DIR` как ключ карты молча
приехал бы как `api_template_dir`, и приложение не увидело бы переменную,
которую читает.

Генерируется **одна** инструкция `ENV` (один слой) в порядке объявления.
Значение попадает в неё как есть: `$` раскрывает Docker, литерал пишется как
`$$`.

### `fetch`

| Поле | Обязательное | Значение |
|---|---|---|
| `name` | Да | Имя записи, `^[a-z0-9_-]+$`. Из него выводятся имена стадий (`fetch-<name>`, а при digest на платформу ещё и `fetch-<name>-<arch>`) |
| `url` | Да | Ссылка, только `https`. Может содержать `${TARGETARCH}` и `${TARGETOS}` |
| `to` | Да | Абсолютный путь в образе |
| `mode` | Нет | Режим файла, по умолчанию `0755` |
| `checksum` | Нет | Либо один digest `sha256:<64 hex>`, либо карта платформа → digest |

Файл приезжает в **своей стадии** и копируется в runtime:

```dockerfile
FROM scratch AS fetch-tool
ARG TARGETARCH
ARG TARGETOS
ADD --checksum=sha256:… --chmod=0755 https://…/tool-linux-${TARGETARCH} /fetched/tool
```

```dockerfile
# финальная стадия
COPY --from=fetch-tool /fetched/tool /usr/local/bin/tool
```

Почему стадия, а не `ADD` прямо в финальную: там пришлось бы объявить `ARG
TARGETARCH`, а `ARG` обесценивает кеш всех слоёв под собой; и только отдельные
стадии позволяют выбрать контрольную сумму по архитектуре (см. ниже). Режим
ставит сама инструкция: `ADD` по URL оставляет файл неисполняемым, а `chmod`
потребовал бы shell, которого в `scratch` нет. `RUN` в стадии не появляется,
поэтому эмуляция ей не нужна, хотя собирается она под целевую платформу.

Ссылка может упоминать только `${TARGETARCH}` и `${TARGETOS}` — переменную,
которой в стадии никто не даёт значения, отвергает загрузка конфига (иначе она
отрендерилась бы пустой и скачивание молча ушло бы в 404). `http` отвергается:
файл и так приезжает в образ, непроверяемая загрузка по открытому каналу —
единственный случай, где digest нужен больше всего.

**Контрольная сумма на каждую архитектуру.** Один digest не может покрыть файл,
имя которого несёт архитектуру, а выбрать digest внутри одной стадии Dockerfile
не умеет. Поэтому карта `платформа → digest` генерирует стадию на каждую
объявленную архитектуру и селектор:

```dockerfile
FROM scratch AS fetch-tool-amd64
ARG TARGETARCH
ARG TARGETOS
ADD --checksum=sha256:1111… --chmod=0755 https://…/tool-linux-${TARGETARCH} /fetched/tool
FROM scratch AS fetch-tool-arm64
ARG TARGETARCH
ARG TARGETOS
ADD --checksum=sha256:2222… --chmod=0755 https://…/tool-linux-${TARGETARCH} /fetched/tool
FROM fetch-tool-$TARGETARCH AS fetch-tool
```

`TARGETARCH` в `FROM` разрешается в глобальной области, объявлять его там не
нужно; BuildKit собирает только ту стадию, на которую пришла ссылка, поэтому
сборка под одну архитектуру скачивает один файл.

Карта требует объявленных `platforms` и ровно по одному digest на каждую из них:
digest для платформы, под которую образ не собирают, — мёртвая конфигурация, а
платформа без digest осталась бы непроверенной (селектор не нашёл бы её стадию).
Два симметричных отказа на загрузке конфига: один digest при ссылке с
`${TARGETARCH}` (проверял бы файл одной архитектуры суммой другой) и карта при
ссылке без него.

**Требование к окружению сборки.** `ADD --checksum` появился в Dockerfile
frontend 1.6, то есть во встроенном frontend Docker Engine 25.0+. Парсерную
директиву `# syntax=docker/dockerfile:1.6`, которая подтянула бы frontend на
более старом движке, сгенерированный файл нести **не может**: директива обязана
быть первой строкой, а там стоит disclaimer генератора. На более старом движке
`checksum` объявлять нечем — `fetch` без него требует только `--chmod`
(frontend 1.3+, то есть любой движок с BuildKit, который сгенерированный проект
и так требует для `--mount=type=cache` в builder-стадии).

### `stages`

| Поле | Обязательное | Значение |
|---|---|---|
| `name` | Да | Имя стадии, `^[a-z0-9_-]+$`. Из него выводится имя в Dockerfile (`stage-<name>`) |
| `image` | Да | Базовый образ стадии |
| `workdir` | Нет | `WORKDIR` стадии, абсолютный путь |
| `run` | Да | Команды стадии, одна инструкция `RUN` на элемент. Минимум одна, каждая — однострочная |
| `copy` | Да | Что runtime-стадия забирает из стадии: `{from, to}`, оба пути абсолютные. Минимум один |

```dockerfile
FROM --platform=$BUILDPLATFORM node:22-alpine AS stage-npmtools
ARG TARGETARCH
ARG TARGETOS
RUN npm install -g --prefix /opt/npm --os=${TARGETOS} --cpu=$(case "${TARGETARCH}" in amd64) echo x64;; 386) echo ia32;; *) echo "${TARGETARCH}";; esac) some-cli@3.3.3
```

**Стадия закреплена за платформой сборщика** (`--platform=$BUILDPLATFORM`).
Иначе мультиплатформенная сборка выполняла бы её по разу на каждую целевую
платформу под эмуляцией — тот самый QEMU, от которого уходит кросс-компилирующая
builder-стадия. Ключа «собирать на целевой платформе» нет намеренно.

Из этого следует главное ограничение: всё архитектурно-зависимое внутри стадии
обязано **назвать цель явно**. `TARGETARCH` и `TARGETOS` объявлены в стадии
`ARG`-ами ровно для этого. Нативный бинарь, приезжающий через npm как optional
dependency (как у `esbuild`), иначе скачается под архитектуру сборщика.

**Словарь архитектур у Docker и у инструмента, скорее всего, разный, и значение
придётся переводить.** `--cpu` npm сверяет со значениями `process.arch` Node, а
`TARGETARCH` несёт имя Docker: 64-битный x86 — это `x64` против `amd64`,
32-битный — `ia32` против `386` (`arm64` и `arm` совпали). Переданный npm как
есть, `--cpu=amd64` не подходит ни под один пакет `@scope/linux-*`, и npm
**молча** ставит инструмент без нативного бинаря — то есть ровно то, от чего
называние цели должно было защитить:

```console
$ docker run --rm node:22-alpine sh -c 'for c in amd64 x64; do rm -rf /opt/n; \
    npm install -g --prefix /opt/n --os=linux --cpu=$c esbuild@0.24.0 >/dev/null 2>&1; \
    echo "cpu=$c: $(find /opt/n -type d -name "linux-*")"; done'
cpu=amd64:
cpu=x64: /opt/n/lib/node_modules/esbuild/node_modules/@esbuild/linux-x64
```

Поэтому перевод стоит в самой команде (она обязана остаться однострочной):

```yaml
run:
  - npm install -g --prefix /opt/npm --os=${TARGETOS} --cpu=$(case "${TARGETARCH}" in amd64) echo x64;; 386) echo ia32;; *) echo "${TARGETARCH}";; esac) some-cli@3.3.3
```

Переведены оба расхождения, а не одно: `platforms` допускает любую
`linux/<арх>`, и на `linux/386` рецепт без ветки `386` молча поставил бы
инструмент без нативного бинаря — тот же дефект, что `--cpu=amd64`, только
обнаруженный позже. `arm64` и `arm` проходят через `*` как есть, потому что в
обоих словарях называются одинаково. Архитектура за пределами этих четырёх
требует сверки со **словарём самого инструмента** (у npm это значения
`process.arch` Node: `ppc64le` там, например, называется `ppc64`) — общего
правила перевода нет, оно своё у каждого инструмента.

`--os` переводить не нужно: платформа объявляется только как `linux/<арх>`
(см. [`platforms`](#platforms)), а `linux` в обоих словарях один и тот же.

**Стадия не получает контекст сборки.** Версия инструмента закрепляется в самой
команде (`cli@3.3.3`), как в секции [`generator`](custom-generators.md):
копирование контекста инвалидировало бы стадию инструментов на каждое изменение
исходников. `npm ci` по проектному lockfile из стадии поэтому не делается —
это установка по пину в команде.

**Префикс npm копируется целиком, а не одним `bin/`.** `npm install -g --prefix
/opt/npm` кладёт в `/opt/npm/bin` **относительные** симлинки
(`prettier -> ../lib/node_modules/prettier/bin/prettier.cjs`). Скопированный
один, `bin/` даёт в образе висящие ссылки, и инструмент не запускается
(`not found`, exit 127). Два рабочих варианта: весь префикс в системный
(`from: /opt/npm`, `to: /usr/local` — ссылки разрешаются в
`/usr/local/lib/node_modules/…`, а `/usr/local/bin` уже в `PATH`, это форма
примера выше) или префикс как есть (`to: /opt/npm`) плюс `env` с
`PATH=/opt/npm/bin:$PATH`.

**CLI из npm требует рантайма в образе.** Инструмент на JS не запустится от
того, что его файлы скопированы: в финальной стадии нужен `node` — из
`base_image` или из `packages`. Сочетание «shell-less база + инструмент на JS»
конфиг проверить не может: что именно нужно инструменту, знает только проект.

Стадия годится и для того, чего `fetch` не умеет: `ADD` не распаковывает
архивы, скачанные по URL, поэтому релиз в `tar.gz` разворачивается стадией
(`FROM alpine` + `RUN wget … | tar -x …`) и копируется из неё.

### Общие проверки

Назначения в образе (`copy.to`, `fetch.to`, `stages[].copy.to`) проверяются
вместе, одним набором:

- путь обязан быть абсолютным, чистым, без пробелов и кавычек и не корнем
  образа;
- `/service`, `/public` и `/etc/onlineconf` занимает сам сгенерированный образ —
  запись туда означала бы, что одна из двух копий молча теряется;
- два объявления с одним назначением отвергаются: в образе победило бы то,
  которое скопировалось последним.

Любой из четырёх ключей у приложения, которое **не** собирает docker-артефакт
(`artifacts` без `docker`), — ошибка генерации, как и `platforms`: ключи
формируют только `Dockerfile-<app>`, то есть из них не сгенерировалось бы
ничего.

**Имена стадий Dockerfile** (`fetch-<name>`, `fetch-<name>-<arch>`,
`stage-<name>`) проверяются так же — вместе, одним набором, и проверяются
именно **сгенерированные** имена, а не имена записей `fetch`/`stages`. Повтор
отвергается на загрузке конфига: второй `FROM` с тем же именем переопределил бы
первый, BuildKit сообщает об этом лишь предупреждением (`DuplicateStageName`),
а `COPY --from` одной записи забрал бы в образ файл другой.

Одна запись генерирует больше одной стадии, поэтому имени записи для проверки
не хватает: `fetch` с digest на платформу даёт стадию на каждую объявленную
архитектуру (`fetch-tool-amd64`), и запись с именем `tool-amd64` порождает
стадию с тем же именем, хотя имена записей различаются. Отвергается в любом
порядке объявления — коллизия это свойство сгенерированных имён, а не того,
какая запись объявлена первой.

Имя записи `fetch` и имя записи `stages` при этом могут совпадать: префиксы
стадий разные (`fetch-tools` и `stage-tools` — две разные стадии).

### Порядок в сгенерированном файле

```text
стадии web-<name>          (секция web)
стадии fetch-<name>        (fetch)
стадии stage-<name>        (stages)
builder
финальная стадия:
    RUN <packages>
    COPY <copy.from> <copy.to>
    COPY --from=fetch-<name>
    COPY --from=stage-<name>
    COPY --from=builder /service /public /etc/onlineconf
    ENV
    WORKDIR
    CMD / ENTRYPOINT
    EXPOSE, ARG, LABEL
```

Вспомогательные стадии стоят **выше** builder'а: `COPY --from` разрешается
только в стадию, объявленную раньше в файле.

Проектные дополнения стоят **выше копии бинаря**, по той же причине, по которой
выше неё стоит установка пакетов: `/service` меняется на каждой сборке, и
слои под ним пересобирались бы вместе с ним — включая скопированный префикс
инструмента, самый дорогой из них. Побочный эффект: при вложенном пересечении
путей (`copy` в `/etc` против `/etc/onlineconf` самого образа) последним
копируется образ, то есть его собственное содержимое проектное дополнение не
затирает. Прямое совпадение назначений отвергается раньше, на загрузке конфига
(см. [«Общие проверки»](#общие-проверки)).

- парсинг и валидация секций — `internal/pkg/config/docker.go` (`Docker.Parse` и
  `AppDocker.Parse`), вызывается из `GetConfig` через `Docker.IsValid` и
  `AppDocker.IsValid`; дополнения runtime-стадии (`copy`, `env`, `fetch`,
  `stages`) — `internal/pkg/config/app_docker_runtime.go`
  (`AppDocker.parseRuntimeAdditions`);
- нормализованный вид и хелперы шаблонов — `internal/pkg/ds/docker.go`
  (`ds.DockerConfig`, `ds.AppDockerConfig`, `Apps.HasDockerPlatforms`) и
  `internal/pkg/ds/app_docker_additions.go` (`AppDockerCopy`, `AppDockerEnv`,
  `AppDockerFetch`, `AppDockerStage` и их директивы);
- проверка «платформы без docker-артефакта» — в `Generator.processConfig`, где
  известен эффективный список артефактов приложения;
- шаблоны — `app/files/Dockerfile.tmpl`, `main/Makefile.tmpl`,
  `main/docker-compose-dev.yaml.tmpl`.
