# Контекст: один корень на процесс

У сгенерированного приложения ровно **один** корень контекста, и его создаёт генератор —
`mainCtx` в `cmd/<app>/psg_main_gen.go`. Всё остальное от него происходит.

Корень контекста — это место, где в картину входит сервисная обвязка: инстанс OnlineConf,
логгер, реестр метрик, отмена процесса (`SIGTERM` → graceful shutdown). Именно потому, что
корень один и его строит сама обвязка, чтение конфигурации не спрашивает, есть ли дерево, а
строка лога не спрашивает, куда писать.

## Почему `context.Background()` в рукописном коде запрещён

Контекст, построенный **рядом** с настоящим корнем, не несёт ничего из перечисленного:

- чтение OnlineConf разыменовывает инстанс, которого в контексте нет (`invalid memory address`);
- строка лога уходит в никуда;
- горутина переживает shutdown, который должна была уважать.

Паника здесь — лучший из исходов. Хуже код, который её «обработал»: читатель, берущий дефолт при
отсутствующем дереве, превращает misconfiguration в правдоподобный ответ.

Реальный случай из потребителя: TUI-презентер перечитывал данные на
`context.WithCancel(context.Background())`, ридер настроек видел «OnlineConf нет» и тихо
деградировал к дефолту. Экран показывал не то, что произойдёт при запуске, — ни ошибки, ни
строки лога.

Поэтому `configs/golangci-lint.yml` сгенерированного проекта запрещает оба имени:

```yaml
forbidigo:
  analyze-types: true
  forbid:
    - pattern: '^context\.(Background|TODO)$'
      msg: "new root contexts are not allowed: …"
```

Свойства правила:

- **`analyze-types: true`** — совпадение по разрешённому пакету, а не по тексту в месте вызова:
  `ctx "context"` + `ctx.Background()` прошло бы мимо правила, написанного на
  `context.Background`. Гейт, который обходится алиасом импорта, — не гейт.
- **Исключение только для сгенерированных файлов**, и не списком: `exclusions.generated: lax`
  выводит из проверки каждый файл с заголовком `Code generated … DO NOT EDIT.`, то есть все
  `psg_*` — включая оба `psg_main_gen.go`, где корень и живёт. Ведённый руками список
  исключений расходился бы с набором приложений проекта.
- **`_test.go` НЕ исключён** — намеренно. Тест берёт контекст из тестовой обвязки
  (`t.Context()`) или из генерируемой фикстуры (ниже), а тест, который строит голый корень, —
  это ровно тот случай, ради которого правило существует: там молчаливый ответ дефолтом
  заметить труднее всего.
- **Производные формы не запрещены**: `context.WithCancel`, `context.WithTimeout`,
  `context.WithValue`, `context.WithoutCancel` над тем контекстом, который вам передали, — это
  и есть ответ.

!!! note "Гейт — `make lint`, и у правила нет своего валидатора"

    В отличие от карты метрик и карты ключей OnlineConf, отдельной цели вроде
    `make context-validate` нет. Следствие — известная дыра, та же, что у `gochecknoinits` и
    `gochecknoglobals`: `exclusions.generated: lax` выводит из проверки `psg_*`-файл **целиком**,
    включая секцию ручного кода ниже disclaimer-маркера. Дыра принята осознанно: ручной код
    ниже маркера — это код, который пишут рядом с уже существующим `mainCtx`, то есть в месте,
    где корень под рукой.

    `make lint` проверяет только diff (`--new-from-rev=origin/main`), поэтому в существующем
    проекте правило краснит **новый** код. Уже написанные вызовы покажет `make lint-full`.

## Производный контекст: `internal/pkg/appctx.Detach`

Остаётся случай, из-за которого за корнем и тянулись: работа, которая **не должна** прекращаться
вместе с родителем — фоновая задача, запущенная из хендлера, который уже ответил; таймаут
shutdown, который обязан отработать после отмены родителя.

```go
// internal/pkg/appctx
func Detach(parent context.Context, timeout time.Duration) (context.Context, context.CancelFunc)
```

Возвращает контекст, который несёт **всё то же**, что `parent`, и **не отменяется** вместе с ним,
плюс функцию отмены. Положительный `timeout` даёт производному контексту свой дедлайн; ноль или
меньше — не даёт, и тогда контекст заканчивает только возвращённая `cancel`.

```go
func (s *Service) scheduleReport(ctx context.Context, id string) {
	// Хендлер уже ответил — его ctx вот-вот отменится, а отчёт надо досчитать.
	bg, cancel := appctx.Detach(ctx, 30*time.Second)

	go func() {
		defer cancel()

		// Читается из того же дерева OnlineConf, что и в хендлере.
		timeout, err := occonf.WorkerJobTimeout(bg, "reporter")
		...
	}()
}
```

Детали:

- **Одна точка входа**, а не семейство функций: каждому проекту нужно от производного контекста
  одно и то же — сохранить значения, снять отмену родителя, — а опциональный таймаут это
  параметр, а не вторая функция.
- **`cancel` возвращается всегда**, и `defer cancel()` корректен в обеих формах. Без таймаута это
  единственное, что когда-либо завершит контекст.
- Внутри — `context.WithoutCancel(parent)`: сохраняются значения (дерево OnlineConf, логгер,
  trace id запроса), снимаются только отмена и дедлайн. Это замена «перенести нужные значения
  руками»: список ключей для переноса устаревает в тот момент, когда обвязка получает ещё один.
- **Это не способ получить контекст там, где его нет.** `parent` обязан быть тем контекстом,
  который вам передали: отделиться от корня, построенного рядом с настоящим, значит отделиться
  от ничего и ничего не унести.

## Контекст в тестах: `occonftest.Context`

```go
// internal/pkg/occonf/occonftest
func Context(tb testing.TB, values map[string]string) context.Context
```

Возвращает контекст, несущий **настоящее** дерево конфигурации со значениями, которые объявил
тест: `values` — это карта «полный путь OnlineConf → значение в нём». Передавайте константы и
построители путей пакета `occonf`, а не рукописные строки, — в этом смысл карты ключей.

```go
func TestSupervisorReapsStaleAgents(t *testing.T) {
	ctx := occonftest.Context(t, map[string]string{
		occonf.PathSupervisorMinLifetime: "11m",
		occonf.PathSupervisorMaxAgents:   "7",
	})

	// occonf.SupervisorMinLifetime(ctx) вернёт 11m — из дерева, а не объявленный дефолт 5m.
}
```

- **Значения — строки**, потому что дерево хранит строки; типизированные аксессоры их разбирают.
  Так что `"11m"` для duration-ключа и `"7"` для int-ключа — ровно то, что прочитал бы
  работающий сервис.
- **Путь, которого в карте нет, просто отсутствует**, и это тоже случай, который стоит
  протестировать: аксессор ключа с объявленным дефолтом ответит дефолтом, аксессор опционального
  ключа сообщит об отсутствии, `required` — отдаст `occonf.ErrKeyNotSet`.
- Дерево пишется в `tb.TempDir()` (исчезает вместе с тестом), а контекст происходит от
  `tb.Context()`. Фикстура **принимает `tb`** намеренно: иначе ей пришлось бы строить
  собственный корень контекста — то самое, что убирается.
- **Отдельный пакет**, чтобы `testing` не попадал в граф импортов сервисного бинаря. Внутри
  каталога пакета аксессоров — потому что построить дерево значит позвать библиотеку OnlineConf,
  а `make onlineconf-validate` разрешает это только там.

!!! warning "Проверки «несёт ли контекст дерево» в `occonf` нет"

    `occonf.Initialized(ctx) bool` существовал в unreleased main и **снят** (TOOLS-132). Спросить
    — это то, из чего собирается молчаливая деградация: читатель, отвечающий дефолтом при
    отсутствующем дереве, **скрывает** misconfiguration вместо того, чтобы о ней сообщить. В
    сгенерированном приложении контекст без дерева невозможен, а там, где возможен, ответ —
    фикстура, а не ветка.

    `occonf.Clone` / `occonf.Release` на месте: клон держит mmap-дерево открытым на той версии,
    которую увидел. `Clone` сам сообщает `occonf.ErrNoTree`, если у источника дерева нет.
